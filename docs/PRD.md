# PRD：jcone211 个人技术作品集 V1

- **版本**：1.0
- **状态**：第一版需求基线
- **日期**：2026-08-04
- **产品类型**：静态个人技术作品集 / 内容沉淀站

## 1. 产品背景

用户的目标岗位为 **Java 后端 / AI 应用开发工程师**。单纯简历很难让陌生招聘方迅速判断工程深度、持续产出与 AI 应用落地能力。

因此需要一个内容克制、可快速浏览的个人站点：用清晰的技术定位、可核验的 GitHub 贡献、项目案例和人工筛选的市场宽度分析，形成可访问的技术名片。

## 2. 产品目标

### 2.1 业务目标

1. 让陌生招聘方在 2 分钟内理解候选人的技术方向与核心能力。
2. 用可点击代码仓库、可见项目界面和 GitHub 贡献日历，降低能力验证成本。
3. 让市场宽度分析成为持续内容资产，同时展示 Agent 辅助研究与人工复核的工作方式。
4. 为未来成熟的 Dify Agent、工作流和其他已部署服务预留入口。

### 2.2 成功标准

- 首页能直接回答“你是谁、做什么、凭什么可信”。
- 招聘方可在不登录站点的情况下访问 GitHub、查看项目说明和阅读市场宽度文章。
- 项目状态透明：已展示能力、进行中能力和未开放能力清晰区分。
- 网站可作为纯静态站点构建和部署；构建失败不会泄露 GitHub Token。

## 3. 目标用户与使用场景

| 用户 | 核心问题 | 期望动作 |
| --- | --- | --- |
| 招聘方 / 用人经理 | 这个候选人是否具备 Java 后端与 AI 应用交付能力？ | 浏览首页，查看技术栈、GitHub 日历和项目案例。 |
| 技术面试官 | 项目中是否有可追溯的工程细节？ | 阅读项目页，进入 GitHub 仓库，查看实现和迭代。 |
| 技术同行 | 对市场宽度分析及 Agent 实践有何方法？ | 阅读人工校对后的市场宽度文章与 Agent 技术说明。 |
| 站点维护者（用户本人） | 如何低成本持续维护内容？ | 手动粘贴、校对 Markdown 后发布文章；构建时更新 GitHub 日历。 |

## 4. V1 用户旅程

1. 招聘方从简历、GitHub 或个人链接进入首页。
2. 首屏看到 Java 后端 / AI 应用定位和能力概览。
3. 通过 Contribution Calendar 判断持续输出情况，并可进入 GitHub Profile。
4. 进入“同花顺问财辅助工具”项目页，查看界面截图、项目背景、已实现能力与仓库链接。
5. 进入“市场宽度分析 Agent”项目页，理解 Agent 的输入输出与展示边界。
6. 进入市场宽度分析栏目，阅读人工确认后发布的文章。

## 5. 功能需求

### FR-01 首页与品牌定位（已实现）

- 首页首屏必须展示：`Java Backend · AI Applications`、Java 后端工程实践、AI Agent / 工作流实践与交付导向。
- 首屏提供“查看项目”和“访问 GitHub”两个明确入口。
- 视觉气质参考 `n9o.xyz` 的简洁、留白和个人技术名片感，但不复制其内容或品牌元素。

**验收标准**

- 首屏在桌面与移动视图均可阅读，不依赖个人头像。
- 招聘方无需滚动即可理解候选人的目标岗位和能力方向。

### FR-02 导航与基础站点能力（已实现）

- 导航必须包含：首页、项目、市场宽度分析、GitHub。
- 支持站内搜索、深浅色外观切换、回到顶部、文章目录、代码复制和结构化面包屑。
- 默认中文，日期时区为 Asia/Shanghai。

### FR-03 GitHub Contribution Calendar（已实现数据流程）

- 首页必须展示近一年 GitHub Contribution Calendar、贡献总数、更新时间和 GitHub Profile 跳转入口。
- 日历数据在**构建/部署时**生成，不在访客浏览器实时请求 GitHub API。
- 若没有提供 `GITHUB_TOKEN`，站点可继续构建，但保留已有日历数据并明确显示未刷新状态。

**验收标准**

- Token 不进入仓库、静态页面、浏览器请求或日志输出。
- 刷新成功后，日历按周和天展示颜色、日期与贡献数。
- GitHub 网络/API 失败时，构建任务给出明确错误，避免生成误导性数据。

### FR-04 项目案例：同花顺问财辅助工具（已实现）

- 展示项目背景、当前可展示能力、产品截图、项目状态和 GitHub 仓库入口。
- 明确表达该项目仍在持续迭代，不能夸大为完全完成的产品。
- 当前可展示能力包括：标的列表管理、快速打开页面、刷新间隔、行情变化、价格提醒、持仓与垃圾池区分。

### FR-05 项目案例：市场宽度分析 Agent（已实现）

- 说明 Agent 的用途：在本地生成每日市场宽度分析 Markdown 草稿。
- 说明内容发布链路：Agent 生成 → 人工复核/挑选 → Hugo 文章发布。
- 明确不提供 Agent 登录、在线体验或投资建议。

### FR-06 市场宽度分析文章（已实现框架）

- 站点提供独立栏目与文章模板。
- 用户可手动新建 Markdown、粘贴本地分析结果、人工校对后将 `draft` 设为 `false` 发布。
- 每篇文章须包含“仅用于研究记录，不构成投资建议”的声明。

### FR-07 未来服务入口（V1 仅预留）

- 信息架构允许后续增加已部署服务入口。
- 只有完成稳定性、访问控制与体验验证的服务才能作为公开入口展示。
- 未完成的 Dify Agent / 产品文案工作流在 V1 不以成品身份展示。

## 7. 非功能需求

- **性能**：作为静态站点输出；首屏不依赖额外后端请求获取贡献日历。
- **安全**：Token 仅存在于构建时环境变量；不保存到 `.env`、源码或生成页面。
- **可维护性**：新增市场文章只需创建 Markdown；新增项目不应要求改动业务代码。
- **真实表达**：对项目完成度、AI Agent 访问边界与分析风险保持透明。
- **界面范围**：V1 不提供独立无障碍功能面板；页面保持基础语义化结构和明确链接文本。

## 8. V1 范围外

- Agent 对外登录、运行和计费能力。
- 市场宽度文章自动每日发布。
- 私有项目、敏感业务数据或凭据展示。
- 在线简历投递表单、用户系统、评论系统、CMS 后台；个人简历 Markdown 将在后续由用户上传，不在本次改动中预置。
- 未完成 Dify Agent/工作流的公开产品化展示。
